Getting started

Build API integrations from your terminal

Connect is a CLI for creating TypeScript integrations, fetching data from APIs, and writing validated records as NDJSON.

Experimental

The project is currently version 0.1.0. Public APIs and local storage formats may change.

Command
beetl-connect
Record output
NDJSON
Integrations

From API to NDJSON

Define an API's inputs, authentication, record schema, and sync behavior in one integration.ts file. The CLI validates it, runs it, persists checkpoints, and writes the records. 

beetl-connect configure .
beetl-connect sync . --output records.ndjson
beetl-connect pack .

Installation

Node.js 24.2 or newer is required. The package includes the SDK and everything needed by the CLI.

Global CLI

To make beetl-connect available system-wide, install the same package globally: 

npm install --global @beetlio/connect

Project-local CLI

Install Connect in an integration project and run it with npx:

npm install @beetlio/connect
npx beetl-connect --help

Create an integration

Create integration.ts. This complete example fetches a GitHub user's public repositories. 

import { defineIntegration, input, z } from "@beetlio/connect";

const Repository = z.object({
  id: z.number(),
  name: z.string(),
  html_url: z.url(),
});

export default defineIntegration({
  key: "github",
  displayName: "GitHub repositories",
  connection: { origin: "https://api.github.com" },
  syncs: (defineSync) => [
    defineSync({
      key: "repositories",
      displayName: "Repositories",
      mode: "snapshot",
      records: Repository,
      primaryKey: ["id"],
      inputs: input.object({
        user: input.string({ label: "GitHub user", default: "octocat" }),
      }),
      async run(ctx) {
        const user = encodeURIComponent(ctx.config.sync.user);
        const response = await ctx.fetch(`/users/${user}/repos?per_page=100`);
        if (!response.ok) throw new Error(`GitHub returned ${response.status}`);
        await ctx.emit({
          records: z.array(Repository).parse(await response.json()),
        });
      },
    }),
  ],
});

Provider request boundary

Paths passed to ctx.fetch() must be relative to the configured origin and begin with /. Absolute and scheme-relative URLs are rejected. Request promises must be awaited; requests still running when the integration returns are cancelled. Emits and logs already submitted before return are settled in order.

Runtime validation

Connection and sync configuration uses input.object() and the non-secret input.* field helpers. Authentication uses separate credential.* descriptors. Each descriptor directly owns its parser and manifest representation. Records and checkpoints use ordinary Zod schemas.

Configure and run it

Configure the integration, then run it. Calling sync first opens the same configuration flow when the default profile or connection is missing. 

beetl-connect configure . repositories
beetl-connect sync . repositories --output repositories.ndjson
head -n 1 repositories.ndjson

Use --profile name for another saved configuration, or configure to update one explicitly. Without --output, Connect writes a timestamped NDJSON file in the current directory.

Authentication

Authentication is declared on the connection. The CLI collects its credentials and adds authentication to provider requests. Integration code never receives credentials or provider-issued OAuth state directly.

Type Declaration Request behavior
None auth.none() No authentication added
Bearer auth.bearer() Adds an Authorization bearer token
Basic auth.basic() Adds HTTP Basic authentication
API key auth.apiKey(...) Adds a header or query parameter
Custom auth.custom(...) Maps multiple credentials to headers or query parameters
Token exchange auth.tokenExchange(...) Exchanges credentials for a cached, expiring bearer token
OAuth 2.0 auth.oauth2AuthorizationCode(...) Uses an access token and can refresh after a 401
Transport requirement

Authenticated requests require HTTPS. Loopback HTTP is allowed for local tests and fixtures.

Named connections

configure collects connection and sync inputs as one JSON object and prompts separately for credentials so secret fields remain masked. It authenticates and verifies before saving either object. Existing credentials and OAuth state are retained unless --reauthorize is supplied. Integration code sees none of these secrets. 

beetl-connect configure . repositories --connection default \
  --inputs '{"connection":{},"sync":{"user":"octocat"}}'

The local authorization-code flow uses http://localhost:53682/oauth/callback; register that redirect URI with the provider. It uses PKCE and either a public client or client_secret_post. Hosted authorization does not use the loopback address: the platform owns its public callback, exchanges the code, and stores the resulting authorization state. Redirect addresses therefore do not belong in uploaded integration source.

Sync behavior

Append syncs

Append is the default mode. Each emitted batch is appended to the output file. If the sync declares a checkpoint schema, the latest emitted checkpoint is persisted and can be supplied to the next run.

Snapshot syncs

A sync with mode: "snapshot" writes to a temporary file. Connect replaces the previous output only after the run and all pending writes succeed. Snapshot syncs cannot declare checkpoints.

Pagination

ctx.paginate() supports cursor, offset, and provider-supplied next-URL pagination. It validates page records and includes response status and normalized headers on each yielded page. An optional hasMorePath points to a response boolean that explicitly controls whether pagination continues. Continuations are followed across empty pages; malformed or repeated continuations fail the sync, and a run is limited to 10,000 pages. Integrations can use ctx.fetch() directly when a provider requires a different strategy.

Retries

The CLI retries safe methods for common transient HTTP statuses and transport failures. A connection can override or disable the policy. Provider response bodies are limited to 16 MiB. 

retry: {
  maxAttempts: 5,
  statuses: [429, 502, 503, 504],
  methods: ["GET"],
  initialDelayMs: 500,
  maxDelayMs: 30_000,
}

CLI reference

Command Description
configure <integration> [key] [--profile <name>] [--connection <name>] [--origin <url>] [--inputs <json>] [--reauthorize] Configure inputs, authenticate, and verify.
sync <integration> [key] Run one sync and write NDJSON records. The key is optional for a single-sync integration.
pack <integration> Create an npm package for a hosted build.

Common options

Option Purpose
--connection name Use a named connection instead of default
--profile name Use a named profile instead of default
--origin url Override the provider origin for configure
--inputs json Provide connection and sync input objects
--reauthorize Collect credentials and authorize again
--output path Override the NDJSON output path
--state path Override the checkpoint state path
Trusted code

Integrations are executable code. Only configure, pack, or run integrations you trust. Hosted builds must treat uploaded source packages as untrusted.

pack accepts a self-contained npm application containing integration.ts, package.json, and the committed package-lock.json. It uses npm pack --ignore-scripts for npm's standard file selection, then adds the lockfile to the resulting .tgz. package.json must contain an explicit files allowlist. Connect rejects npm-selected files outside it and private runtime paths at any depth, then prints the included files. Package metadata, README, and license files remain implicit. Registry dependencies and npm aliases are supported; pack rejects local paths, workspaces, Git repositories, and remote tarballs. Dependency declarations must exactly match the lockfile root. 

{ "files": ["integration.ts", "src", "icon.png"] }

The npm package is transport, not a trusted build artifact: pack does not compile or execute the integration. A hosted platform must safely unpack it in an untrusted build job, enforce package limits, run npm ci --ignore-scripts, validate the exact upload, and call the same builder used by the local CLI: 

import { buildIntegration } from "@beetlio/connect/builder";

const { bundle, manifest, sdkVersion } = await buildIntegration("/workspace/integration");

The builder produces the Node.js 24.2 runtime bundle and manifest and records its SDK version. It resolves integration imports of @beetlio/connect to that SDK, so Core does not duplicate compiler or validation rules. The bundle validates its definition against the build manifest when loaded and uses canonical source-map paths for reproducible artifacts. Runtime jobs execute the immutable result in gVisor on an isolated node pool. Local sync uses the same builder and Node.js target. Use ctx.fetch() for managed authentication, retries, and origin enforcement; direct external requests receive none of the connection's managed credentials.

Hosted v1 treats uploaded integrations as tenant-admin-approved executable code. gVisor isolates workloads from platform infrastructure, but it does not prevent integration code or an npm dependency from forwarding fetched data elsewhere. Third-party marketplace integrations require a separate egress policy and are outside the first release.

Profiles and named connections are stored with owner-only permissions in the operating system's user configuration directory: $XDG_CONFIG_HOME/beetl-connect on Linux, ~/Library/Preferences/beetl-connect on macOS, and %APPDATA%\beetl-connect\Config on Windows. Connections contain credentials and OAuth authorization state where applicable. Saved secrets are bound to the provider origin and authentication definition. Connections are not encrypted. Profiles and connections carry revisions; changed inputs and explicit reauthorization create new revisions, while automatic OAuth refresh preserves them. Sync checkpoints remain under .beetl/state and are isolated by those revisions. Only one local process may use a state path at a time. Configuration and OAuth-backed syncs also lock their named connection so authorization refresh cannot race. Concurrent operations fail instead of waiting. If a process is forcibly killed, remove its adjacent .lock file only after confirming no operation still uses it.

Running the Wikidata sync

The entities sync calls Wikidata's wbsearchentities API. It returns search-result metadata rather than complete claims or relationships.

Local commands use the default profile. If it does not exist, the CLI prompts for one JSON object containing the declared inputs before continuing. 

beetl-connect sync examples/wikidata entities

For automation, supply the same validated input object non-interactively:

beetl-connect configure examples/wikidata entities \
  --inputs '{"connection":{"userAgent":"my-wikidata-sync/1.0 (me@example.com)"},"sync":{"search":"open source","language":"en","maxResults":25}}'
beetl-connect sync examples/wikidata entities

Output record

{
  "id": "Q39162",
  "label": "open source",
  "description": "philosophy about free redistribution and access to a product",
  "aliases": [],
  "url": "https://www.wikidata.org/wiki/Q39162"
}

maxResults defaults to 100 and accepts values from 1 through 500. pageSize defaults to 25 and accepts values from 1 through 50.

Wikidata structured data is available under CC0. Automated clients must follow Wikimedia's API usage guidelines.

Current scope

Connect is a standalone local CLI and integration toolkit. It supports named connections. Local connection files are owner-readable but are not encrypted, and there is no registry or sandbox for untrusted integrations.
