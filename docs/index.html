Getting started

Build API integrations from your terminal

Connect is a CLI for creating TypeScript integrations, fetching data from APIs, and writing validated records as NDJSON.

Experimental

The project is currently version 0.0.0. Public APIs and local storage formats may change.

Command
beetl-connect
Record output

From API to NDJSON

Define an API's inputs, authentication, record schema, and sync behavior in one integration.ts file. The CLI checks it, runs it, persists checkpoints, and writes the records. 

beetl-connect check .
beetl-connect sync . --output records.ndjson
beetl-connect pack .

Installation

Node.js 24.2 or newer is required. The package includes the SDK and everything needed by the CLI.

Global CLI

To make beetl-connect available system-wide, install the same package globally: 

npm install --global @beetlio/connect

Project-local CLI

Install Connect in an integration project and run it with npx:

npm install @beetlio/connect
npx beetl-connect --help

Create an integration

Create integration.ts. This complete example fetches a GitHub user's public repositories. 

import { defineIntegration, input, z } from "@beetlio/connect";

const Repository = z.object({
  id: z.number(),
  name: z.string(),
  html_url: z.url(),
});

export default defineIntegration({
  key: "github",
  displayName: "GitHub repositories",
  connection: { origin: "https://api.github.com" },
  syncs: (defineSync) => [
    defineSync({
      key: "repositories",
      displayName: "Repositories",
      mode: "snapshot",
      records: Repository,
      primaryKey: ["id"],
      inputs: input.object({
        user: input.string({ label: "GitHub user", default: "octocat" }),
      }),
      async run(ctx) {
        const user = encodeURIComponent(ctx.config.sync.user);
        const response = await ctx.fetch(`/users/${user}/repos?per_page=100`);
        if (!response.ok) throw new Error(`GitHub returned ${response.status}`);
        await ctx.emit({
          records: z.array(Repository).parse(await response.json()),
        });
      },
    }),
  ],
});

Provider request boundary

Paths passed to ctx.fetch() must be relative to the configured origin and begin with /. Absolute and scheme-relative URLs are rejected.

Runtime validation

Connection and sync configuration uses input.object() and the non-secret input.* field helpers. Authentication uses separate credential.* descriptors. Each descriptor directly owns its parser and manifest representation. Records and checkpoints use ordinary Zod schemas.

Check and run it

Check the integration before running it. The first sync prompts for declared inputs and saves them in the local default profile. 

beetl-connect check .
beetl-connect sync . repositories --output repositories.ndjson
head -n 1 repositories.ndjson

Use --profile name for another saved configuration, or configure to update one explicitly. Without --output, Connect writes a timestamped NDJSON file in the current directory.

Authentication

Authentication is declared on the connection. The CLI collects its credentials and adds authentication to provider requests. Integration code never receives credentials or provider-issued OAuth state directly.

Type Declaration Request behavior
None auth.none() No authentication added
Bearer auth.bearer() Adds an Authorization bearer token
Basic auth.basic() Adds HTTP Basic authentication
API key auth.apiKey(...) Adds a header or query parameter
Custom auth.custom(...) Maps multiple credentials to headers or query parameters
Token exchange auth.tokenExchange(...) Exchanges credentials for a cached, expiring bearer token
OAuth 2.0 auth.oauth2AuthorizationCode(...) Uses an access token and can refresh after a 401
Transport requirement

Authenticated requests require HTTPS. Loopback HTTP is allowed for local tests and fixtures.

Named connections

connect prompts for the connection inputs and credentials declared by the integration. For OAuth, the provider callback produces separate authorization state containing access and refresh tokens. Integration code sees none of these secrets. 

beetl-connect connect . --connection default
beetl-connect verify . --connection default

Sync behavior

Append syncs

Append is the default mode. Each emitted batch is appended to the output file. If the sync declares a checkpoint schema, the latest emitted checkpoint is persisted and can be supplied to the next run.

Snapshot syncs

A sync with mode: "snapshot" writes to a temporary file. Connect replaces the previous output only after the run and all pending writes succeed. Snapshot syncs cannot declare checkpoints.

Pagination

ctx.paginate() supports cursor, offset, and provider-supplied next-URL pagination. It validates page records and includes response status and normalized headers on each yielded page. An optional hasMorePath points to a response boolean that explicitly controls whether pagination continues. Continuations are followed across empty pages; malformed or repeated continuations fail the sync, and a run is limited to 10,000 pages. Integrations can use ctx.fetch() directly when a provider requires a different strategy.

Retries

The CLI retries safe methods for common transient HTTP statuses and transport failures. A connection can override or disable the policy. Provider response bodies are limited to 16 MiB. 

retry: {
  maxAttempts: 5,
  statuses: [429, 502, 503, 504],
  methods: ["GET"],
  initialDelayMs: 500,
  maxDelayMs: 30_000,
}

CLI reference

Command Description
pack <integration> Build a self-contained, Deno-compatible .beetl.zip artifact.
check <integration> Type-check and validate an integration.
configure <integration> [key] [--profile <name>] [--connection <name>] Configure sync inputs and select a named connection.
connect <integration> [--connection <name>] [--origin <url>] Create or reauthorize a named connection.
verify <integration> [--connection <name>] Run the integration's verification function for a named connection.
sync <integration> [key] Run one sync and write NDJSON records. The key is optional for a single-sync integration.

Common options

Option Purpose
--connection name Use a named connection instead of default
--profile name Use a named profile instead of default
--origin url Override the provider origin for connect
--output path Override the NDJSON output path
--state path Override the checkpoint state path
Trusted code

Integrations are executable code. Only check, pack, or run integrations you trust. Artifact digests detect corruption; they do not verify the author.

pack accepts an entry file or directory containing integration.ts. It type-checks source with the bundled TypeScript compiler and bundles local imports and installed npm dependencies into neutral ESM. Dependencies must be declared and pinned by an npm v3 package-lock.json. Connect never installs packages or runs dependency lifecycle scripts. Other commands also accept a packed .beetl.zip. An artifact contains the bundle, manifest, Deno runtime declaration, license notices, integrity metadata, and inline source maps without source contents. Neutral bundling rejects Node built-ins and other unresolved imports. Provider traffic must use ctx.fetch(). These checks improve compatibility but are not a sandbox.

Artifact hashes detect corruption, not provenance. A hosted platform must accept source workspaces, install their committed npm graph with lifecycle scripts disabled in an untrusted build sandbox, and record the artifact digest it produced. It must not trust an uploaded artifact merely because its self-declared hashes match.

Profiles and named connections are stored with owner-only permissions in the operating system's user configuration directory: $XDG_CONFIG_HOME/beetl-connect on Linux, ~/Library/Preferences/beetl-connect on macOS, and %APPDATA%\beetl-connect\Config on Windows. Connections contain credentials and OAuth authorization state where applicable. Saved secrets are bound to the provider origin and authentication definition. Connections are not encrypted. Profiles and connections carry revisions; changed inputs and explicit reauthorization create new revisions, while automatic OAuth refresh preserves them. Sync checkpoints remain under .beetl/state and are isolated by those revisions.

Running the Wikidata sync

The entities sync calls Wikidata's wbsearchentities API. It returns search-result metadata rather than complete claims or relationships.

Local commands use the default profile. If it does not exist, the CLI prompts for the declared inputs before continuing. 

beetl-connect sync examples/wikidata entities

Automation can provision connections/wikidata/default.json under the operating system's user configuration directory with this shape: 

{
  "integration": "wikidata",
  "name": "default",
  "revision": "22222222-2222-4222-8222-222222222222",
  "provider": {
    "origin": "https://www.wikidata.org",
    "authentication": { "type": "none" }
  },
  "inputs": { "userAgent": "my-wikidata-sync/1.0 (me@example.com)" },
  "credentials": {}
}

The profile at profiles/wikidata/entities/default.json in the same directory then selects that connection and contains only sync inputs: 

{
  "integration": "wikidata",
  "sync": "entities",
  "connection": "default",
  "revision": "11111111-1111-4111-8111-111111111111",
  "inputs": { "search": "open source", "language": "en", "maxResults": 25 }
}

Generate a new UUID revision whenever directly provisioned inputs or authorization change. configure and connect manage revisions automatically.

Output record

{
  "id": "Q39162",
  "label": "open source",
  "description": "philosophy about free redistribution and access to a product",
  "aliases": [],
  "url": "https://www.wikidata.org/wiki/Q39162"
}

maxResults defaults to 100 and accepts values from 1 through 500. pageSize defaults to 25 and accepts values from 1 through 50.

Wikidata structured data is available under CC0. Automated clients must follow Wikimedia's API usage guidelines.

Current scope

Connect is a standalone local CLI and integration toolkit. It supports named connections. Local connection files are owner-readable but are not encrypted, and there is no registry or sandbox for untrusted integrations.

Advanced: custom hosts

The CLI is the primary interface. Applications that need to execute Deno-compatible artifacts with their own authentication, request, and persistence services can implement the optional SyncHost interface from @beetlio/connect/host. See the runnable custom host example. SyncHost is a capability boundary, not a sandbox. Custom executors must prevent integration code from reaching providers directly; production isolation and provider-egress enforcement belong outside the integration runtime.
